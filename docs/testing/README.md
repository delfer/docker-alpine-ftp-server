# План полного тестирования FTP-образа

Исследован **delfer/docker-alpine-ftp-server**, commit `8989ee25e7bc6ff12bc9af41ee9433737ac3e842`, совпадающий с GitHub `master` на 12 ноября 2026 года. Прочитаны все пять tracked-файлов, история из 47 коммитов, 53 issues, 32 PR с diff и 182 комментария/ревью. Код сервера в этой задаче не изменялся.

Результат: **341 именованный тест-кейс в 18 разделах**, шесть полных матриц с **508 комбинациями**, инструкции по реализации и реестр всех источников. Это спецификация будущих тестов; существующей автоматической suite пока нет. Исследовательские пробы, перечисленные ниже, проверяют только свои конкретные условия.

## Как читать

Начать реализацию можно с IMPLEMENTATION.md, затем брать кейсы по ID. Повторно изучать все issues для первой очереди не требуется.

## Обязательные режимы

Active/passive — выбор способа создания data connection клиентом. `pasv_enable=YES` не запрещает active. Control connection и data connection тестируются раздельно.

| ID профиля | Control | Data | Команда | Кто инициирует data TCP |
| --- | --- | --- | --- | --- |
| ftp-pasv | Plain FTP | Plain | PASV | Клиент |
| ftp-epsv | Plain FTP | Plain | EPSV | Клиент |
| ftp-port | Plain FTP | Plain | PORT, IPv4 | Сервер |
| ftp-eprt | Plain FTP | Plain | EPRT, AF1 | Сервер |
| ftps12-pasv | Explicit FTPS, AUTH TLS | TLS, PROT P | PASV | Клиент |
| ftps12-epsv | Explicit FTPS, AUTH TLS | TLS, PROT P | EPSV | Клиент |
| ftps12-port | Explicit FTPS, AUTH TLS | TLS, PROT P | PORT, IPv4 | Сервер |
| ftps12-eprt | Explicit FTPS, AUTH TLS | TLS, PROT P | EPRT, AF1 | Сервер |

Восемь профилей образуют `all8`. Базовый FTPS pin — TLS 1.2 для воспроизводимого теста reuse. Все четыре способа дополнительно обязательны с TLS 1.3 в MX-TLS13. TLS 1.0/1.1, plain login/data на TLS-сервере, implicit FTPS, SFTP и IPv6 — самостоятельные позитивные/негативные/конфигурационные случаи, а не пропущенные клетки.

## Комбинации

| Матрица | Полное произведение | Количество |
| --- | --- | ---: |
| MX-CORE | 8 режимов × 6 профилей users × 3 storage × 2 топологии | 288 |
| MX-PAYLOAD | 8 режимов × 9 размеров | 72 |
| MX-NAMES | 8 режимов × 12 имён | 96 |
| MX-RECOVERY | 2 security × 2 home × 3 storage × 2 lifecycle events | 24 |
| MX-READONLY | 8 режимов × 3 политики read-only | 24 |
| MX-TLS13 | 4 data-команды × TLS 1.3 | 4 |

508 — число записей в этих произведениях, **не число независимых новых требований поверх 341 кейса**. Кейс может проверяться несколькими комбинациями; дубликаты одинаковых условий можно объединить, сохранив все IDs в отчёте. Остальные конкретные сочетания — TLS × certificate errors, mode switching, NAT × wrong ADDRESS, mixed UID, chroot × paths, interruption × concurrency — перечислены в каталоге. Для них нельзя заменять все варианты одним удобным happy path.

Конечный каталог не является доказательством покрытия любого мыслимого поведения vsftpd/ядра/Docker. Граница аудита: текущий код, вся доступная история этого репозитория и перечисленные протокольные, эксплуатационные и конфигурационные классы. Новые фичи/платформы добавляют случаи с новыми ID.

## Первые задачи

1. Создать Docker fixtures и exact-mode FTP/FTPS-клиент; выполнить восемь roundtrip-профилей и негативный TLS reuse.
2. Реализовать USR/GRP, FS-003/004, LIFE-004/017 и DOC-005: они ловят уже обнаруженные проблемы.
3. Добавить файловые операции, полный MX-CORE, payload/names/read-only/recovery, ошибки и восстановления.
4. Подключить suite к PR CI, затем добавить нагрузку, остальные архитектуры и независимые клиенты.
5. FUT/decision реализовывать после выбора соответствующего контракта. Открытый PR не делает функцию частью текущего API.

P0 — критичность, а не обещание, что тест уже зелёный. `contract` проверяет текущую поддержку; `known-defect` — конкретную обнаруженную регрессию; `characterization` сначала устанавливает baseline; `hardening` задаёт желаемое усиление; `decision` требует выбрать политику; `future` относится к ещё не реализованной функции.

## Что реально проверено

Собран текущий исходный код на amd64; выполнен FTP smoke через опубликованные Docker-порты. В отдельной Docker-сети выполнены STOR, RETR, NLST, DELE и проверка bytes во всех восьми профилях, затем во всех четырёх профилях TLS 1.3. Сервер отверг TLS 1.0 и 1.1; клиент без data-session reuse получил `522 SSL connection failed: session reuse required`.

Наблюдены: потеря второго user после explicit UID, игнорирование GID без UID, modes `750`/`2755` в зависимости от порядка создания home, возможность `CWD /` по default config, а также один startup exit при раннем подключении. Полная матрица из 508 комбинаций, стресс, все архитектуры и GUI-клиенты **не запускались**.
